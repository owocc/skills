# pixel-perfect-restore — 100% 还原设计稿

把设计稿 1:1 还原为可运行的前端产物：布局、尺寸、颜色、字体、圆角、阴影、图片资源全部对齐设计稿，最终以截图差分对比验收通过。

## 产物与目录约定

工作区有既有规范时优先遵循项目规范；没有时按以下默认位置落盘，保证产物可追溯：

| 目录 | 内容 |
|---|---|
| `design/` | 设计稿基准截图与关键局部参考图 |
| `assets/` | 导出素材 + `manifest.md` 素材清单 |
| `plans/` | 页面与组件规划文档（第 6 步产出） |
| `reports/` | 验证记录：实现截图、差异清单、修正结果 |
| 源码 | 落在项目既有源码结构中；无既有约定时才新建 `src/` |

## 工作流 (Workflow)

1. **设计稿链接**（必须，第一步）：先向用户拿到设计稿链接，拿到后立即尝试验证能否访问：
   - **先识别可用 MCP**：确认当前环境配置了哪个设计工具 MCP（Ardot、Figma 等，按实际配置判断，**不绑定特定工具**）；下文与引用文件里的工具名均为示例，按实际可用 MCP 对应到同类能力。
   - **可访问** → 记录链接与目标画板，进入下一步。
   - **未登录** → 调用设计工具 MCP 为用户发起登录请求（如 Ardot 的授权流程），等登录成功后重试访问。
   - **权限不足 / 无法访问** → **立即停止，不得继续后续任何步骤**；把具体问题告诉用户（哪个工具、什么错误、链接与所需权限），待用户解决权限后再重新开始。
2. **上下文检索**：当工作区为代码仓库时，先读懂项目再动手，不放过任何能确定当前代码规范的线索：
   - **优先阅读**：`README`、`AGENTS`、`DESIGN` 文档，以及已有页面代码——了解项目规范、特殊处理与既有实现方式。
   - **特殊处理重点排查**：构建层是否配置了 `px to rem`（ `px-to-viewport` 等）转换插件、样式变量与主题机制、API 路由约定——这类处理会直接改变写码时的单位与取值方式。
   - **参考其他页面**：获取其他页面的代码，了解项目的图片引用、代码组织、样式编写方式（单位、命名、目录结构），新页面与它们保持同一套写法。
3. **解析需求**： 开始还原前，先询问用户是否有一份 **页面交互文档**（各屏关系、页面跳转、点击 / 滑动等交互行为、状态切换的说明）。后续阶段的写法取决于这份文档是否存在，不要跳过这一步。
   - **有** → 作为交互实现的依据，与页面 / 状态归类一并纳入后续规划。
   - **没有** → 不要反复追问阻塞流程：按纯静态还原实现，交付时统一列出「推测的交互行为 / 待确认点」。
4. **读取设计稿信息**：后续一切以这一步拿到的数据为准，先补齐再继续：
   - **三类数据**：① 画板树与布局结构；② 节点属性（尺寸、坐标、颜色 / 渐变、字体字号、圆角、阴影、图片填充）；③ 基准截图（整画板 + 关键局部）。
   - **工具映射（示例）**：结构与属性用 `capture_layout`（浅层）与 `batch_read`（深层、按需拉属性）；文件与画板清单用 `fetch_file_info` / `fetch_editor_state`；基准截图用 `capture_screenshot`；颜色 / 字体 token 用 `fetch_variables` / `fetch_styles` / `export_variables`。Figma MCP 对应 `get_metadata`（结构）、`get_code`、`get_screenshot`（基准）、`get_variable_capsules`（token）。
   - **先看树，再取细节**：先拿画板整体结构与各模块 bounds，再对需要的节点取样式细节；深层节点读不全时换用能拉深度的读取方式（见附录）。
   - **预加载**：这一步的数据要全部进入上下文后再进入后续步骤——导出素材判断背景组、写码取数值、验证对比基准都靠它；基准截图存入 `design/`。
5. **导出素材**：**导出前必读引用文件：[references/asset-export.md](references/asset-export.md)** —— 素材导出指南：尺寸倍率确认、背景组整组导出（强制）、头像等运行时数据处理、判重归一存储、manifest 清单格式与模板。按该文件执行，不要凭记忆。
6. **编程约束**：
   - **页面关联先行**：编写代码前先确认本次设计稿里有哪些页面是相互关联的（跳转、共用模块）。**页面名称信息量很大**（文本虽少），很多设计稿页面其实是同一页面的不同状态表现——先把页面按“页面 / 状态”归类，再决定文件结构，避免同一页面被当成多个独立页面重复实现。
   - **生成前先产出「页面与组件规划」**：项目使用组件化框架（Vue / React / Solid 等，非纯 HTML）时，不要把所有内容堆进一个大文件；为方便后期接入数据，**拆分组件是必要的，且必须规划到代码生成之前**——先将整个设计稿的所有页面、各页面用到的组件、页面间共享的组件整理成一份规划文档（页面清单 → 每页的组件拆分 → 共享组件归属），确认后再进入 1:1 复刻。纯 HTML 产物也按“大模块”划分区块结构，同理先行规划。
   - **组件优先复用**：制作交互组件前，先查询代码库内是否已有可用组件（含交互行为），有则直接用；**严禁修改代码库内原有组件**，不够用时新建包装或新组件。代码风格与库内其他页面保持一致（见第 2 步上下文检索的结论）。
   - **样式取值对齐设计稿**：字体、文本颜色等样式与设计稿保持一致，不自创近似值；单位与取值方式遵循第 2 步查明的项目规范（如 px→rem 转换）。
   - **语义化标签 + data-id 回溯点**：用语义化标签构建结构，并给重要的大模块加**唯一 `data-id`**（如 `data-id="family-card"`），方便后续修改时直接提及定位、验证截图时对块归因、以及设计稿节点到代码的回溯。
   - **文本集中管理**：页面内文本类内容不硬编码散落各处：
     - 用户有多语言需求 → 先探索仓库内已有的多语言方案（i18n 框架 / 文案文件），接入它；
     - 没有 → 先将本页所有文本集中存到**单个文件**（如 `texts.js` / `copy.ts`）导入页面使用，防止后续接入或修改文案时需要遍历整个代码库。
7. **验证阶段**：用截图对页面和设计稿基准进行视觉对比，量化验收，不靠目测：
   - **验收方法**：同尺寸逐行 / 逐列平均差扫描定位问题带 + 互相关找最优位移（先对齐结构，再对齐字形）；结构性差异（区块位移、列差、缺素材、断层）必须清零，剩余差异仅允许字体渲染噪声。
   - **无头截图注意**：Chrome headless 最小窗口宽 500px，`--window-size=402` 无效（`#page` 会被居中偏移）——用大窗（600×2000）截图再按偏移（(600-402)/2=99px）裁出页面；需等字体 / 图片加载：`--virtual-time-budget≥6000`。
   - **真实接入区域降级验收**：对可替换 / 可滚动等真实接入区域（用户头像、动态列表、接口数据展示位等），不要求逐像素对比——只验收**框架与布局**（位置、尺寸、对齐、圆角容器）和**素材使用**（是否用了正确的切图 / 占位、@Nx 尺寸是否正确），内容本身留待运行时。
   - **可接受的偏差**（不要为消除它们无限迭代）：
     - 字体度量差异（设计稿 SF Pro vs 浏览器 SF NS）导致换行点不同：按设计稿断行位置硬断行 + 负字距（约 -0.55px）微调；每行内字形残差属字体渲染噪声；
     - 背景图 @2x 缩到 @1x 显示时，浏览器重采样与设计稿渲染有轻微软化，纹理密集区残差偏高属正常。
